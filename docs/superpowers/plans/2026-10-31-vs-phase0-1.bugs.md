# Bugs found while writing the Phase 1 regression tests

Plan: `2026-10-31-vs-phase0-1-sync-and-regression.md`. Found by characterisation work; **not fixed in Phase 1** (tests
only). Each entry is fixed in the module step that owns the code, or earlier as its own fix PR if the owner wants.

### B68: photo upload takes the file extension from the client filename unchecked

**risk:** security
**status:** open (found 2026-10-31 by T113; fix belongs to the `people` module, step 4, or a standalone `fix/b68` PR)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:186-188`

`ext = file.filename.rsplit('.', 1)[-1].lower()` and `filename = f'{uuid.uuid4()}.{ext}'` are joined into
`UPLOAD_DIR`. A filename without a dot becomes the whole extension; a filename such as `a.png/../../x` makes `ext`
contain path separators, so the written path leaves `UPLOAD_DIR`. The content type is client-supplied and only checked
against the allow-list, not against the bytes. The endpoint is admin-only, which limits the exposure (DP-01, R-new).

Fix: derive the extension from the validated content type (`{'image/jpeg': 'jpg', 'image/png': 'png', 'image/webp':
'webp'}`), never from the filename; reject when the mapping has no entry.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B68 -q` (a test posting `a.png/../../x` with content type `image/png` expects 200 and a file named `<uuid>.png` inside `UPLOAD_DIR`, nothing outside it)

### B72: `/api/locations/live` and the `location_update` push disagree on `sos_active`

**risk:** security
**status:** open (found 2026-10-31 by the final review of Phase 1; fix belongs to the `tracking`/`sos` modules, step 3, where the thin payload is designed; router and hardware reader are security-critical paths)
**Files:**
- Modify: `bee-with-me/backend/routers/locations.py:36` or `bee-with-me/backend/hardware_reader/reader.py:141-144` (the reader's comment at line 140 claims they match)

`/live` computes `(le.sos_active AND sa.id IS NOT NULL)`; the WebSocket payload sends only the open-alert `EXISTS`.

which is what the SOS banner already assumes) and use it in both places.

### B73: HID read buffer has no size cap

**risk:** security
**status:** open (found 2026-10-31 by the fix wave of Phase 1; fix belongs to the `gateway` module, step 3, validated on real hardware)
**Files:**
- Modify: `bee-with-me/backend/hardware_reader/hid_reader.py:165-170`

`buf += chunk` grows without limit while no `##…@CRC\r\n` frame completes, so sustained line noise on the HID device
grows the buffer until memory runs out (BP-01: the reader must survive a noisy gateway). Fix: cap the buffer (a frame is
under 200 bytes; drop the buffer and log once when it exceeds, for example, 1 KiB). Related step-3 decision, not a bug
by itself: an ignored repeat does not reset the 15 s dedupe timer (`hid_reader.py:100-103`), so a device whose ACKs are
lost gets the same event stored again 15 s after the first copy; a test pins today's behaviour.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B73 -q` (a `run()` test feeding 2 KiB of noise without `##` sees the buffer dropped and the reader still alive)

### B75: uploads are read into memory without a size cap (photo upload and Excel import)

**risk:** security
**status:** open (found 2026-11-07 by the security-reviewer on the B71 fix; low; for a tech-debt session, `people` module)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:192` (`upload_photo`: `f.write(await file.read())`)
- Modify: `bee-with-me/backend/routers/users.py:275` (`import_volunteers`: `raw = await file.read()`)

Both routes read the whole request body with `await file.read()` and no ceiling, and `import_volunteers` then hands the
bytes to pandas/openpyxl/calamine. A very large upload, from an admin or a stolen admin token, can exhaust the server's
memory (the same host runs the reader and the live map). Both routes are admin-only, which limits the exposure.

Fix: one helper `_read_capped(file, limit)` that reads in chunks and raises `HTTPException(413)` once the total passes
the limit (for example 5 MiB for photos, 10 MiB for Excel; constants next to `UPLOAD_DIR`), used in both routes before
any parsing or writing. Check `Content-Length` first when present, but do not rely on it.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B75 -q` (Expected: PASS; a test posting a body one byte over the limit to `/api/users/import` and to `/api/users/{id}/photo` expects 413 and no file written / no DB call; a body at the limit still gets 200)

### B76: exception text is returned to the client in the import path

**risk:** security
**status:** open (found 2026-11-07 by the security-reviewer on the B71 fix; low; for a tech-debt session, `people` module)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:301` (`detail=f'Could not parse file: {e}'`)
- Modify: `bee-with-me/backend/routers/users.py:350` (`skipped.append({'row': row_num, 'reason': str(e)})`)

Raw parser and database exception text (library internals, and for asyncpg errors possibly column names, constraint names
or values) goes back to the caller in the 400 detail and in the `skipped[].reason` of the 200 response. Only admins can
call the route, so this is internal-detail disclosure to an admin, not an outside leak. `UniqueViolationError` at line 348
already has a fixed message and stays as it is.

Fix: answer with a fixed message (`Could not parse file` / reason `could not be saved`) and log the exception on the
server with `logger.warning('import row %s failed: %s', row_num, e)` (%-style, per the project rule; add the `logger`
if the module has none).

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B76 -q` (Expected: PASS; a file no engine can parse gives 400 whose detail has no exception text; an INSERT raising `RuntimeError('secret-detail')` gives a `skipped` reason without `secret-detail`, and the log has it)

### B79: Excel import picks "Имейл" as the name column

**risk:** low
**status:** open (found 2026-11-07 by the breaker on the B71 fix; the `people` module)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:251-256` (`_find_col`) and `:306`

`_find_col` matches keywords as substrings of the lower-cased header, so after B71 `'име'` also matches `Имейл`
(e-mail) and, in a sheet where no `volunteer`, `name` or `доброволец` header exists, an `Имейл` column placed left of
`Име` becomes the name column. A header like `Фамилно име` placed first has the same effect. Fix: try an exact
(trimmed, case-folded) header match for each keyword first, then the substring match, and skip headers containing
`имейл` / `email`.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B79 -q` (Expected: PASS; a sheet `['Имейл', 'Име', 'ПИН']` creates the row from the `Име` column, a sheet `['Фамилно име', 'Име']` uses `Име`)
