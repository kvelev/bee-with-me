# Bugs found while writing the Phase 1 regression tests

Plan: `2026-10-31-vs-phase0-1-sync-and-regression.md`. Found by characterisation work; **not fixed in Phase 1** (tests
only). Each entry is fixed in the module step that owns the code, or earlier as its own fix PR if the owner wants.

### B68: photo upload takes the file extension from the client filename unchecked

**risk:** security
**status:** fixed (4134209)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:186-188`

`ext = file.filename.rsplit('.', 1)[-1].lower()` and `filename = f'{uuid.uuid4()}.{ext}'` are joined into
`UPLOAD_DIR`. A filename without a dot becomes the whole extension; a filename such as `a.png/../../x` makes `ext`
contain path separators, so the written path leaves `UPLOAD_DIR`. The content type is client-supplied and only checked
against the allow-list, not against the bytes. The endpoint is admin-only, which limits the exposure (DP-01, R-new).

Fix: derive the extension from the validated content type (`{'image/jpeg': 'jpg', 'image/png': 'png', 'image/webp':
'webp'}`), never from the filename; reject when the mapping has no entry.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B68 -q` (a test posting `a.png/../../x` with content type `image/png` expects 200 and a file named `<uuid>.png` inside `UPLOAD_DIR`, nothing outside it)

### B73: HID read buffer has no size cap

**risk:** security
**status:** open (found 2026-10-31 by the fix wave of Phase 1; fix belongs to the `gateway` module, step 3, validated on real hardware)
**Files:**
- Modify: `bee-with-me/backend/hardware_reader/hid_reader.py:165-170`

`buf += chunk` grows without limit while no `##…@CRC\r\n` frame completes, so sustained line noise on the HID device
grows the buffer until memory runs out (BP-01: the reader must survive a noisy gateway). Fix: cap the buffer (a frame is
under 200 bytes; drop the buffer and log once when it exceeds, for example, 1 KiB). Related step-3 decision, not a bug
by itself: an ignored repeat does not reset the 15 s dedupe timer (`hid_reader.py:100-103`), so a device whose ACKs are
lost gets the same event stored again 15 s after the first copy; a test pins today's behaviour.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B73 -q` (a `run()` test feeding 2 KiB of noise without `##` sees the buffer dropped and the reader still alive)

### B75: uploads are read into memory without a size cap (photo upload and Excel import)

**risk:** security
**status:** fixed (fe4a668)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:192` (`upload_photo`: `f.write(await file.read())`)
- Modify: `bee-with-me/backend/routers/users.py:275` (`import_volunteers`: `raw = await file.read()`)

Both routes read the whole request body with `await file.read()` and no ceiling, and `import_volunteers` then hands the
bytes to pandas/openpyxl/calamine. A very large upload, from an admin or a stolen admin token, can exhaust the server's
memory (the same host runs the reader and the live map). Both routes are admin-only, which limits the exposure.

Fix: one helper `_read_capped(file, limit)` that reads in chunks and raises `HTTPException(413)` once the total passes
the limit (for example 5 MiB for photos, 10 MiB for Excel; constants next to `UPLOAD_DIR`), used in both routes before
any parsing or writing. Check `Content-Length` first when present, but do not rely on it.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B75 -q` (Expected: PASS; a test posting a body one byte over the limit to `/api/users/import` and to `/api/users/{id}/photo` expects 413 and no file written / no DB call; a body at the limit still gets 200)

### B76: exception text is returned to the client in the import path

**risk:** security
**status:** fixed (8edeae6)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:301` (`detail=f'Could not parse file: {e}'`)
- Modify: `bee-with-me/backend/routers/users.py:350` (`skipped.append({'row': row_num, 'reason': str(e)})`)

Raw parser and database exception text (library internals, and for asyncpg errors possibly column names, constraint names
or values) goes back to the caller in the 400 detail and in the `skipped[].reason` of the 200 response. Only admins can
call the route, so this is internal-detail disclosure to an admin, not an outside leak. `UniqueViolationError` at line 348
already has a fixed message and stays as it is.

Fix: answer with a fixed message (`Could not parse file` / reason `could not be saved`) and log the exception on the
server with `logger.warning('import row %s failed: %s', row_num, e)` (%-style, per the project rule; add the `logger`
if the module has none).

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B76 -q` (Expected: PASS; a file no engine can parse gives 400 whose detail has no exception text; an INSERT raising `RuntimeError('secret-detail')` gives a `skipped` reason without `secret-detail`, and the log has it)

### B80: the multipart body is buffered to disk before auth runs, and nothing caps the request body

**risk:** security
**status:** open (found 2026-11-07 in the review of `fix/users-hardening` (PR #81); `main.py` and the ingress are security-critical paths; the ingress is outside this repo)
**Files:**
- Modify: `bee-with-me/backend/main.py` (new middleware next to the router includes, around line 266) or the ingress of the environment
- Read: `bee-with-me/deploy/k8s/app/backend.yaml`, `bee-with-me/deploy/k8s/app/kustomization.yaml:3` (the ingress is "supplied by whoever deploys it")

`MAX_PHOTO_BYTES` and `MAX_IMPORT_BYTES` (`routers/users.py:31-32`, enforced by `_read_capped`, `users.py:36-50`, called at `:215` and
`:303`) run inside the handler. FastAPI parses the multipart body, which Starlette spools to a temporary file, before it
resolves `Depends(require_role('admin'))`, so an unauthenticated client can make the server write an arbitrarily large
body to disk and the 401 comes after. The cap in the handler does not help against that. The repo sets no body limit at
any layer: `deploy/docker/nginx.conf` serves only the SPA (`/api` goes through the ingress, see its header comment),
`deploy/k8s/app/*.yaml` has no ingress and no `proxy-body-size` annotation, and uvicorn is started without a limit.
What bee-dev has is **not recorded in the repo**: whoever runs bee-dev must read the ingress annotation
(`nginx.ingress.kubernetes.io/proxy-body-size`, nginx default 1 MiB) or the equivalent and write the value into this
entry. On the field machine uvicorn answers directly with no proxy at all.

Fix: an ASGI middleware that answers 413 when `Content-Length` is above a ceiling (for example 12 MiB) and counts the
bytes of a chunked body without `Content-Length`, checked before the body is read, applied to `/api/users/import` and
`/api/users/{id}/photo`; plus the ingress annotation in the deploy repo, so both layers agree.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B80 -q` (Expected: PASS; an unauthenticated POST to `/api/users/import` with `Content-Length` over the ceiling gets 413 and the temp directory is empty; a request under the ceiling still gets 401 without a token)

### B81: photos are accepted on the client's content type alone, and `/uploads` has no `nosniff`

**risk:** security
**status:** open (found 2026-11-07 in the review of `fix/users-hardening` (PR #81); `routers/users.py` and `main.py` are security-critical paths)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:211-224` (`upload_photo`)
- Modify: `bee-with-me/backend/main.py:271` (`app.mount('/uploads', StaticFiles(...))`)

B68 made the stored extension come from the content type, but the content type is still the client's claim: `:211`
trusts `file.content_type` and `:215-220` write the bytes without looking at them, so an HTML or SVG file posted as
`image/png` is stored as `<uuid>.png`. `StaticFiles` serves by extension and sends no `X-Content-Type-Options`, so a
browser that sniffs content may render it as HTML under the app's origin (stored XSS; only admins upload, which limits
it). Fix: check the first bytes after `_read_capped` (JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, WebP `RIFF....WEBP`)
and answer 400 when they do not match the claimed type; send `X-Content-Type-Options: nosniff` on `/uploads/*` (a small
subclass of `StaticFiles` or a middleware on that prefix).

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B81 -q` (Expected: PASS; `<html>` bytes posted as `image/png` get 400 and no file; a real PNG gets 200; `GET /uploads/<file>` carries `x-content-type-options: nosniff`)

### B82: photo upload leaves an orphan file for an unknown user and keeps the old photo file

**risk:** normal
**status:** open (found 2026-11-07 in the review of `fix/users-hardening` (PR #81); `people` module)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:215-224` (`upload_photo`)

The file is written (`:219-220`) before `UPDATE users SET photo_url = $1 WHERE id = $2` (`:223`), and the result of the
UPDATE is not checked, so an unknown `user_id` answers 200 and leaves `<uuid>.png` in `uploads/` that nothing points to.
The old `photo_url` is overwritten without deleting its file, so every re-upload leaves one more file behind. `uploads/`
holds volunteer photos, so the pile is personal data nobody can find through the app. Fix: look the user up first (404 if
missing, before anything is written), read the old `photo_url`, write the new file, update the row, then remove the old
file when it is inside `UPLOAD_DIR`; remove the new file when the UPDATE fails.

dod:
- `cd bee-with-me; .venv\Scripts\python -m pytest backend\tests --task B82 -q` (Expected: PASS; a photo for an unknown id gets 404 and `UPLOAD_DIR` has no new file; a second upload for a user leaves exactly one file for that user)

### B84: the Excel import has no limit on the number of rows

**risk:** normal
**status:** open (found 2026-11-07 in the review of `fix/users-hardening` (PR #81); `people` module)
**Files:**
- Modify: `bee-with-me/backend/routers/users.py:344` (`for i, row in df.iterrows():`)

`MAX_IMPORT_BYTES` (`:32`) caps the file, not the sheet: a 10 MiB `.xlsx` compresses to far more rows than a volunteer

message.
